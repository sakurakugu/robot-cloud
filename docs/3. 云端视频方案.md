# 云端视频方案

## 背景

之前云端前端请求 `/api/v1/robots/:uuid/video/session` 时，后端只会返回机器狗本体的局域网 WHEP 地址：

- `http://<robotIp>:8889/test/whep`

这意味着：

- 浏览器必须能直接访问机器狗内网 IP
- 前端与机器狗通常需要处于同一局域网
- 云端 HTTPS 页面还会受到浏览器对 HTTP 本地地址的混合内容限制

因此，本地测试可用，但公网云端前端无法稳定观看视频。

## 本次落地方案

本次先实现一个不依赖额外媒体基础设施的可用版：

1. 云端前端请求视频会话
2. 后端在机器人在线时返回 `mode=cloud`、`preferredProtocol=frame`
3. 前端通过业务 WebSocket 发送 `video_subscribe`
4. 后端记录当前页面对该机器人的视频订阅
5. 首个订阅者出现时，后端向机器狗下发 `video_subscribe`
6. 机器狗从本地 `rtsp://127.0.0.1:8554/test` 抽帧
7. 机器狗将每帧编码为 JPEG base64，并通过现有业务 WebSocket 发送 `video_frame`
8. 后端只把 `video_frame` 转发给已订阅该机器人的 UI
9. 前端用 `img` 标签渲染最新一帧
10. 最后一个订阅者离开时，后端向机器狗下发 `video_unsubscribe`

## 当前实现特性

- 机器人在线时，云端前端优先走云端帧流
- 机器人离线时，视频会话直接返回不可用，不再回退本地 WHEP
- 后端会跟踪订阅计数，避免无订阅时机器狗持续抽帧
- 机器人业务连接断开后重新连上，若仍有活跃订阅，后端会自动重新下发 `video_subscribe`
- 机器狗抽帧运行在独立线程中，避免阻塞主事件循环

## 当前限制

这是一个过渡版本，不是真正的媒体服务器方案，主要限制如下：

- 传输的是 JPEG 帧流，不是 H.264/WebRTC
- 带宽占用和延迟都高于局域网 WHEP 直连
- 目前主要适合云端预览、调试和轻量远程操作
- 没有音视频同步，也没有自适应码率

## 后续升级方向

如果后续要升级为正式版低延迟云端视频，建议引入专门媒体链路：

- 机器狗推 H.264 到云端 `mediamtx / SRS / Janus`
- 云端部署 `coturn`
- 前端通过 `WHEP/WebRTC` 或 `HLS` 拉流
- 后端视频会话仅负责鉴权、分配播放地址和会话控制

当前这版的目标不是替代媒体服务器，而是先把“云端可看”这件事做通。
